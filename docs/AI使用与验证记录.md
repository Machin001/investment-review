# AI 使用与验证记录

> 记录 AI 在本项目中参与了哪些环节、产出了什么、以及**哪些输出是错的、怎么被发现和修正的**。
> 这份文档的重点是第三部分 —— 没有错误的 AI 记录通常意味着没有认真验证。

## 一、使用的 AI 工具

| 工具 | 用途 |
|---|---|
| WorkBuddy（内置 Agent，模型 DeepSeek-V4.1-Flash） | 需求分析、架构设计、代码生成、数据接口探查、文档撰写 |
| iFinD MCP `news.search_notice` / `index.sector_data` | **被产品运行时调用**的语义检索能力（不是开发期辅助） |
| 扶摇 REST API | 结构化行情数据（不含生成式能力） |

开发过程中没有把任何 API Key 写入代码或提交到仓库，所有凭证只从环境变量读取。

---

## 二、AI 参与的环节

| 环节 | AI 做了什么 | 人类做了什么 |
|---|---|---|
| 需求界定 | 拆解题目三条硬要求，提出「时点防火墙」作为核心机制 | 否决了「构造数据也能交」的方案，要求接真实数据 |
| 数据探查 | 试调扶摇 10 余个接口、iFinD 37 个工具，摸清参数与返回形态 | 提供两个 Key |
| 架构 | 数据契约、三层归因模型、偏差规则库 | 确认「AI 不算数字」的边界 |
| 代码 | 全部代码由 AI 生成 | 逐轮 review，提出 P0/P1/P2 修改建议（见 `修改建议.md`） |
| 文档 | README、测试说明、本记录 | 校对事实与口径 |
| **产品运行时** | AI 只做文本结构化、追问、证据排序、叙述生成 | — |

**关键的边界决策**：AI 不参与任何数字计算与偏差判定。
归因的 β、行业超额、持有交易日、收益分解全部由代码算出；
偏差由规则库判定，每条规则都是可复算的表达式。这样即使是模型产生了幻觉，也不会污染结论。

## 三、被修正的错误（真实发生，按发现顺序）

### 1. 行业超额用了错误的行业

- **AI 的做法**：在 `review.ts` 里把板块查询硬编码成 `'食品饮料->酒类'`，所有标的都用它。
- **后果**：兆易创新（半导体）的行业超额被算成 **−5.96%**，归因结论完全错。
- **怎么发现**：AI 自己在读联调输出时觉得不对 —— 兆易创新怎么会跟白酒一个行业。
- **修正**：`Trade` 增加 `sectorQuery` 字段，按标的所属行业取数；缺失时整项降级而不是拿别的行业凑数。
- **修正后**：行业超额 **+0.98%**（半导体），五项加总严格闭合。

### 2. 归因五项相加差 0.01

- **AI 的做法**：各项独立 `round2()`，残差用未舍入的浮点数再 `round2()`。
- **后果**：`market + sector + exec + residual` 与 `total` 差 0.01，测试直接失败。
- **修正**：先各自舍入到两位，再由总收益倒推残差，保证恒等。
- **意义**：这不是显示问题 —— 归因面板如果加不起来，用户就没法信任任何一个数字。

### 3. 「没有专门想过什么情况下算错」没被判为空证伪条件

- **AI 的做法**：`EMPTY_FALSIFY` 只匹配 `空 / 没想过 / 没有 / 无 / 未设` 这类短词。
- **后果**：种子数据 T2 里用户写的是「没有专门想过什么情况下算错」，规则漏判，
  这个最重要的偏差没被识别出来。
- **怎么发现**：`tests/review.smoke.test.ts` 断言 `codes` 必须包含 `no_falsify_condition`，测试红了。
- **修正**：正则扩展为否定式表述匹配 `(没有|没|未|不)(专门|认真|仔细)?(想过|设|考虑过|定义过|想好)`。

### 4. 扶摇 `date_ms` 的语义是猜的

- **AI 的做法**：直接写 `new Date(date_ms + 8h)`，隐含假设它是「当日东八区零点」，
  而且这个假设藏在算术里，没有任何地方声明。
- **风险**：如果实际是收盘时刻，所有 A 级证据的 `publishedAtMs` 会整体偏移 15 小时，
  时点防火墙的 visible/after 判定全错，而且**不会报错**。
- **修正**：
  1. 实测核对 `1785686400000 → UTC 2026-08-02T16:00Z → 东八区 08-03 00:00`；
  2. 写成显式常量 + 注释说明实测时间；
  3. 加运行时断言：若 `(date_ms + 8h) % 24h ≠ 0` 直接抛错，而不是静默算错。

### 5. 用自然日冒充交易日

- **AI 的做法**：`tradingDayGapApprox()` 的实现是 `Math.round((b-a)/86400000)` —— 名字叫交易日，
  算的是自然日。
- **后果**：跨国庆长假时「预期 5 个交易日、实际 12 个」这类判断会差 8 天以上，
  而假设台账的 `horizonTradingDays` 恰好要跟它对比。
- **修正**：新增 `getTradingCalendar()`；`tradingDayGap(from, to, calendar)` 必须传日历，
  覆盖不到就抛 `CalendarCoverageError`；自然日版改名 `calendarDayGapBetween` 并注明「仅供展示」。
- **验证**：周五→周一 = 1（自然日 3）；9-30→10-09 = 1（自然日 9）。

### 6. 把数据冲突当成了 bug

- **AI 的做法**：发现同一天 `limit-up-pool` 返回 0 家、`limit-up-statistics` 返回 59 家，
  第一反应是「接口参数写错了」，反复改参数试图让两者一致。
- **修正**：接受这是真实的数据冲突，反手把它做成产品能力 ——
  `Evidence.metric` + `detectConflicts()` 双向标记 `conflictWith`，界面提示「两源不一致，均保留」。
  同时它成了「数据冲突不得静默合并」这条合规要求的固定测试夹具。

### 7. 构建失败误判了三次

- **AI 的判断**：`next build` 报 `EPERM: open '.next/trace'`，先后归因为
  ① 中文路径 ② `NODE_OPTIONS` 注入的 shim ③ 沙箱限制。
  为此做了英文路径对照实验（同样失败，排除①）、清空 NODE_OPTIONS 重试（仍失败，排除②）。
- **真因**：环境里有一个 **safe-delete 拦截器**，Next 清理 `.next` 时批量删除被拦下，
  报错表现为后续 open 失败；叠加当时还残留着一个没退干净的 dev server 占着句柄。
- **教训**：现象层（EPERM 在 trace 上）和原因层（递归删除被拦）可以完全不相关，
  只盯着报错的那一行会一直修错地方。
- **修正**：起服务一律用受管的后台任务并显式收尾，不再用 `( ... &)` 遗留进程。

### 8. iFinD 证据 id 用了数组下标

- **AI 的做法**：`ifind:notice:{date}:{i}`，`i` 是检索结果的下标。
- **后果**：两次检索返回顺序一变，id 就漂移，`conflictWith` 互指、`BiasHit.evidenceIds` 引用、
  会话间去重全部失效。
- **修正**：内容寻址 `sha1(date|title).slice(0,10)`，并补了幂等性测试。

### 9. 正则回溯把「20 日均线」解析成价格 20

- **AI 的做法**：用 `(跌破|低于)\s*(\d+)` 从证伪条件里抽价格阈值，觉得够用了。
- **漏在哪**：加了「数字后面不能是日/%/倍」的负向断言后，测试仍然失败 ——
  因为正则引擎会**回溯**：`20 日` 整体不匹配，就把 `[0-9]+` 退成 `2`，`2` 后面不是「日」，于是匹配成功、
  阈值变成 2 元。
- **修正**：数字前后都加边界断言 `(?<![0-9.])…(?![0-9.])`，并在测试里专门覆盖
  「低于 20 日均线」「亏 8%」「跌穿 39.70」三类用例。
- **教训**：凡是「从自然语言抽数字」，就必须假设用户会写出各种单位，
  并且要意识到回溯会让你的负向断言失效。

### 10. 存储层没有并发保护，冷启动会 500 且丢数据

- **AI 的做法**：`readStore()` 发现文件不存在就写种子，`writeStore()` 直接覆盖写，没有队列。
  首页 `Promise.all(listPositions, listAssets, listDecisions)` 三个调用并发进入。
- **后果（实测复现）**：冷启动时并发请求 → 部分请求 `EPERM: open store.json` → 首页 500；
  更糟的是**并发写入互相覆盖**，5 条并发 `addTrades` 最后只剩 1 条。
- **怎么发现的**：第三轮评审指出后，我先写了一个并发回归测试，一次就红了 ——
  说明这不是理论风险，是必现的。
- **修正**：单飞初始化（共享 Promise）+ 写操作入队串行 + 原子替换（tmp→rename，带重试）+
  落盘失败降级为「内存一致、不抛错」。回归测试连续 3 次通过。
- **教训**：「本地小应用不需要考虑并发」是错的 —— Next.js 的 Server Component
  天然会并发调用数据层，越是「单机」越容易忽略这一层。

## 四、AI 输出被拒绝的设计

| AI 的初始方案 | 被拒绝的原因 | 最终方案 |
|---|---|---|
| 让 LLM 写「你这笔亏损主要归因于追高」 | 无法验证，且会强化错误理论 | 规则库判定 + 硬证据文本 |
| 把残差当作「个股特质贡献」 | 事件驱动与噪声无法分离，属于伪量化 | `idiosyncraticPct` 固定 0，残差单列并说明拆不开 |
| 用自然日近似交易日 | 口径失真 | 交易日历 + 覆盖不足抛错 |
| 事后公告打个「事后」标签但仍展示在列表里 | 标签可以被忽略，等于没拦住 | 从查询层就分组，出口再加护栏 |
| 缺数据时用 0 填充以免界面难看 | 违反「不得静默生成正常结论」 | 显式 gap + 结论降级标注 |

## 五、AI 输出的验证方式

1. **数字可溯源**：每个归因项在 `Attribution.inputs` 里挂着 `sourceEvidenceIds`，
   界面上点开「溯源」能看到来源接口、统计口径与原始字段 JSON。
2. **断言而不是感觉**：`tests/review.smoke.test.ts` 断言五项加总 < 0.01，
   断言 `visible` 中每条都满足 `publishedAt ≤ cutoff`，断言归因入口混入事后证据会抛错。
3. **真实数据联调**：所有数字来自扶摇/iFinD 实测返回，不是 mock。
   种子数据里的价格、日期、热榜排名均可复现。
4. **人工核对**：行业口径错误、首页与复盘页收益口径不一致（+13.12% vs +13.05%）都是人工比对发现的，
   已统一为「价格涨跌（未含费用）」与「区间收益（含费用）」两个明确标注。
